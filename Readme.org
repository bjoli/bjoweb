* bjoweb — a small web framework for Bjolang

Kestrel on one side, fibers on the other, an inbox between them.

#+BEGIN_SRC scheme
(import (bjoweb core))
(import (bjoweb router))
(import (bjoweb server))

(: hello (-bjo-> Request Response))
(defbjo (hello req)
  (text (str "hello, " (request-param-or req "name" "world") "\n")))

(defbjo (main args)
  (serve (router
           (route-get "/"            (fun (req) (html "<h1>bjoweb</h1>")))
           (route-get "/hello/:name" hello))
         #:port 8080)
  0)
#+END_SRC

#+BEGIN_SRC sh
bjo run examples/hello.bjo
#+END_SRC

** Architecture

A .NET web server calls handlers on its own threads, which are not fibers and lack Bjolang's effect handlers, parameters, and cancellation scopes. To bridge this, `bjoweb` runs your code in worker fibers.

The ASP.NET middleware simply posts the ~HttpContext~ into an inbox:

#+BEGIN_SRC scheme
(fun (ctx next) (cast Task (inbox-call/token requests ctx (ctx-aborted ctx))))
#+END_SRC

A worker fiber receives the call with its original environment intact, reads the request, runs your handler, writes the response, and completes the task. This returns the ~HttpContext~ to Kestrel for the next request.

For more details, see ~(std inbox)~.

** The four modules

| Module            | What is in it                                       | ASP.NET? |
|-------------------+-----------------------------------------------------+----------|
| ~(bjoweb core)~   | ~Request~, ~Response~, ~websocket~ and the functions over them | no |
| ~(bjoweb router)~ | routes, patterns, matching                           | no       |
| ~(bjoweb html)~   | SXML as a literal, escaping, rendering               | no       |
| ~(bjoweb server)~ | Kestrel, the inbox, the workers, the two conversions, the upgrade | all of it |

Two thirds of this package never name an ASP.NET type, which is why two thirds
of it can be unit-tested with no socket anywhere:

#+BEGIN_SRC scheme
(router-match app (make-request "GET" "/hello/ada" (map-empty) (map-empty) "" (map-empty)))
;; => (Matched <request with params {"name" "ada"}> <handler>)
#+END_SRC

It is also what the framework's ~(frameworks "Microsoft.AspNetCore.App")~ buys:
declaring it lets ~(bjoweb server)~ *name* ASP.NET types. Your own package needs
no declaration at all unless it names one too — see ~Docs/Projects.org~,
"Shared frameworks".

** A handler

#+BEGIN_SRC scheme
(: show-user (-bjo-> Request Response))
(defbjo (show-user req)
  (match (load-user (request-param-or req "id" ""))
    (None (not-found))
    ((Some u) (json-text (user->json u)))))
#+END_SRC

A handler is a bjoroutine ~(-bjo-> Request Response)~. A handler that doesn't suspend can be an ordinary ~(fun (req) ...)~; the compiler will lift it automatically.

Because handlers return a complete ~Response~ value, nothing is written to the client until the function returns. If a handler raises an exception, the server responds with a clean 500 error instead of a partially written response.

*** Reading the request

| ~(request-method req)~              | ~"GET"~, ~"POST"~ — upper case, as it arrived      |
| ~(request-path req)~                | ~"/hello/ada"~, already percent-decoded            |
| ~(request-body req)~                | the whole body as UTF-8 text, or ~""~              |
| ~(request-param req "id")~          | what ~/users/:id~ bound — an ~Option~              |
| ~(request-query req "page")~        | ~?page=2~, decoded, ~+~ counted as a space         |
| ~(request-form req "email")~        | from an ~application/x-www-form-urlencoded~ body   |
| ~(request-header req "Accept")~     | case-insensitive                                   |
| ~(request-scheme req)~              | ~"http"~ or ~"https"~, as the client asked         |
| ~(request-host req)~                | ~"example.com"~, with the port if there was one    |
| ~(request-client req)~              | the client's address, ~"203.0.113.7"~, no port     |

~request-param~, ~-query~, ~-form~ and ~-header~ each have an ~-or~ form
taking a fallback: ~(request-query-or req "page" "1")~. The last three are what
the client used, which behind a reverse proxy is not what the connection says;
see Behind a proxy.

*** Writing the response

| ~(text "hi")~                  | ~text/plain; charset=utf-8~            |
| ~(html "<p>hi</p>")~           | ~text/html; charset=utf-8~             |
| ~(json-text "{\"a\":1}")~      | ~application/json; charset=utf-8~      |
| ~(respond 418 "no" #:content-type "text/plain")~ | anything else        |
| ~(binary bytes)~               | ~application/octet-stream~, or ~#:content-type~ |
| ~(redirect "/next")~           | 302, or 301 with ~#:permanent #t~      |
| ~(not-found)~ ~(bad-request why)~ ~(method-not-allowed allow)~ ~(server-error)~ | |

All of them take ~#:status~ where a status makes sense, and four combinators
build on any of them:

#+BEGIN_SRC scheme
(with-header (with-status (text "gone") 410) "X-Why" "tidied up")
#+END_SRC

~with-header~ appends rather than replaces, so a response can carry two
~Set-Cookie~ s. ~with-content-type~ and ~with-body~ are the other two.

A response's body is a ~Body~:

| ~Empty~                  | nothing                                    |
| ~(Text string)~          | sent as UTF-8, with no byte order mark     |
| ~(Bytes (Array byte))~   | sent as it is                              |
| ~(Streamed writer)~      | written as it is produced; see Streaming   |
| ~(Upgraded upgrade)~     | what ~websocket~ answers with; see below   |

~(response-body r)~ is the ~Body~, and ~(response-text r)~ is ~(Some s)~ for a
~Text~ body and ~None~ otherwise, for a test or a middleware that wants to look.

~Content-Length~ is set from the body, and one put among the headers is
dropped. A status that cannot have a body — 1xx, 204, 304 — is sent without
one, whatever the handler gave it. A ~HEAD~ answered by a ~GET~ route gets the
~GET~'s ~Content-Length~ and no body.

There is no JSON writer here. ~(text json)~ is one import away, and putting one
in this package would make every program that serves plain text carry it.

*** Middleware Pipeline

A middleware is a function that takes a handler and returns a new handler (`(-> Handler Handler)`). You can compose these cleanly using the `pipeline` function.

Because `pipeline` takes a target handler followed by a variable number of middleware functions, they are applied from right to left, wrapping the handler logically:

#+BEGIN_SRC scheme
(defbjo (main args)
  (def wrapped-home (pipeline home logger auth))
  (serve (router (route-get "/" wrapped-home)) #:port 8080)
  0)
#+END_SRC

Here, `logger` wraps `auth`, which wraps `home`. The request flows through `logger`, then `auth`, then `home`.

** Streaming

A body can be written as it is produced — a large download, the output of a
long computation — rather than built in memory first:

#+BEGIN_SRC scheme
(: countdown (-bjo-> TextOutputPort void))
(defbjo (countdown out)
  (let go ((i 10))
    (when (> i 0)
      (write-string out (str (int->string i) "\n"))
      (flush-port out)
      (ignore (sync (timeout 1000)))
      (go (- i 1)))))

(router (route-get "/countdown" (fun (req) (stream-text countdown))))
#+END_SRC

| ~(stream writer)~        | ~writer~ gets the body as a ~ByteOutputPort~; ~application/octet-stream~ |
| ~(stream-text writer)~   | ~writer~ gets a ~TextOutputPort~ that writes UTF-8; ~text/plain; charset=utf-8~ |

Both take ~#:status~ and ~#:content-type~, and the combinators work on what they
return as on any response. The writer's ports come from ~(std ports)~ and the
prelude: ~write-bytes!~ and ~flush!~ on the byte port, ~write-string~ and
~flush-port~ on the text port.

What is written goes out when the writer flushes, or when the port's buffer
fills. A client that reads slowly makes the writer's writes wait, so a stream
holds no more in memory than one buffer. The length is not known in advance,
so the body goes out chunked; a ~Content-Length~ put among the headers is kept,
and the writer then has to write exactly that many bytes.

*** Where a writer runs

As a websocket session does: on a fiber of its own, so that a long stream holds
no worker, with the environment of the fiber that started the server. The head
— the status and the headers — goes out before the writer is called, so a
client sees the status at once.

- *The writer returns:* the body ends, and the response is complete. The
  server closes the port; the writer does not.
- *The writer raises:* it is logged, and the connection is aborted. The status
  has already gone out, so a 500 is no longer possible, and a client must not
  take what did arrive for the whole body.
- *The client goes away:* the writer is cancelled.
- *The server stops:* the writer is cancelled and the connection aborted, for
  the same reason as when it raises.
- *A ~HEAD~*, or a status that cannot have a body: the head goes out alone, and
  the writer is never called.

*** Server-sent events

For a browser's ~EventSource~: a stream of events, each of them sent whole.

#+BEGIN_SRC scheme
(: count-from (-> int (-bjo-> EventSink void)))
(defun (count-from from)
  (bjoroutine (es)
    (let go ((n from))
      (ignore (send-event! es (int->string n) #:id (int->string n)))
      (ignore (sync (timeout 1000)))
      (go (+ n 1)))))

(router (route-get "/count" (fun (req) (event-stream (count-from 0)))))
#+END_SRC

| ~(event-stream writer)~                      | ~writer~ gets an ~EventSink~; ~text/event-stream~ |
| ~(send-event! sink data #:event "" #:id "")~ | one event; ~#f~ once the stream is over          |

~event-stream~ is a ~stream~ underneath, so its writer runs where a stream's
does, and a writer that raises, a client that goes and a server that stops are
dealt with as they are there. On top of that:

- ~data~ with line breaks in it goes out as several ~data:~ lines, and arrives
  as one string. A line break in ~#:event~ or ~#:id~ would begin a field of its
  own, so ~send-event!~ refuses it with an ~ArgumentException~.
- A comment goes out at once, so that the stream is seen to be open before
  there is anything to say, even through a proxy that holds the head back
  until some body arrives. Another goes out after every ~#:keep-alive~
  milliseconds without an event, 15 seconds unless told otherwise and 0 for
  none, so that nothing on the way closes a quiet stream as idle.
- ~#:retry~ is how many milliseconds the browser waits before reconnecting.
- ~Cache-Control: no-cache~ goes with it, and ~X-Accel-Buffering: no~ for nginx,
  which otherwise buffers.
- ~send-event!~ returns once the event has been handed to the loop that owns
  the port, which writes one thing at a time, keep-alives included. A slow
  client slows the writer, as it does any stream's.

A browser reconnects by itself whenever the stream ends, the writer returning
included, and sends the last ~#:id~ it saw as ~Last-Event-ID~:
~(request-header req "Last-Event-ID")~ is where to carry on from. Like any
header it is the client's to write. Answering anything but 200 — ~204~, say —
is what tells a browser to stop reconnecting.

Over HTTP/1.1 a browser opens at most six connections to one host, and every
open ~EventSource~ holds one of them. Over HTTP/2, which a proxy in front
speaks to the browser, that limit does not bite.

~examples/ticker.bjo~ is a page that counts and carries on from
~Last-Event-ID~ when the stream comes back.

** Websockets

A websocket is a kind of answer. A handler that returns ~(websocket session)~
has decided to accept, and ~session~ runs on the socket:

#+BEGIN_SRC scheme
(import (net websocket protocol))

(: echo (-bjo-> WebSocket void))
(defbjo (echo ws)
  (let go ()
    (match (websocket-next ws)
      ((Some m) (ignore (websocket-send! ws m)) (go))
      (None unit))))

(router
  (route-get "/echo" (fun (req) (websocket echo)))
  (route-get "/chat" (pipeline (fun (req) (websocket chat #:protocol "chat")) require-login)))
#+END_SRC

The socket itself is ~(net websocket protocol)~'s — the [[https://github.com/bjoli/websocket][~(net websocket)~]]
package, which bjoweb depends on — and the same one ~websocket-connect~ in
~(net websocket client)~ gives a client:

| ~(websocket-next ws)~          | the next message, or ~None~ once the socket has closed |
| ~(websocket-recv ws)~          | the same as an event, for a ~choose~               |
| ~(websocket-send! ws m)~       | ~(TextMessage s)~ or ~(BinaryMessage bytes)~; ~#f~ once closed |
| ~(websocket-close! ws #:code 1000 #:reason "")~ | the close handshake, waited for |
| ~(websocket-closed ws)~        | an event that fires with the ~CloseStatus~ once it is over |

Because the upgrade is a ~Response~, whatever runs before it works as it does
for any route: a middleware that answers 401 refuses the socket before it is
opened, and ~with-header~ adds a header to the ~101~. Check ~Origin~ there —
browsers apply no CORS to a websocket, so any page can open one to your server
with your user's cookies. ~examples/chat.bjo~ compares it with ~request-scheme~
and ~request-host~, which are what the browser used, behind a proxy too.

A request to a websocket route that is not a websocket handshake gets ~426~,
or ~400~ for a malformed key, and the session is never called.

*** Where a session runs

Not on a worker. The worker hands the request to a fiber of its own and goes
back to the queue, so a thousand open sockets hold no workers, and the request
is answered — which is what hands the connection back to Kestrel — when the
socket is over. The session has the environment of the fiber that started the
server, as a handler has.

- *The session returns:* the socket is closed with 1000.
- *The session raises:* it is logged, and the socket is closed with 1011.
- *The client closes, or goes away:* the session is cancelled. Leaving a room
  belongs in ~#:finally~, and anything there that waits in a ~with-shield~.
- *The server stops* — ~stop-server!~, or Ctrl-C under ~serve~: every socket is
  closed with 1001. Kestrel's stop waits for the requests in flight, and an
  open socket is one, so without this it would wait out the host's shutdown
  timeout.

~websocket~ takes ~#:protocol~, the ~Sec-WebSocket-Protocol~ to answer with;
~#:max-message~, the largest message after reassembly, 1 MiB unless told
otherwise, above which the socket is closed with 1009; and ~#:keep-alive~, how
many idle milliseconds before a ping, 30 seconds unless told otherwise.

A session is ordinary Bjolang over ~(net websocket protocol)~, so it can be tested with
no server: ~ports->websocket~ over two ~byte-pipe~ s is a socket with nothing
underneath. ~examples/chat.bjo~ is a chat room, page included.

** HTML

#+BEGIN_SRC scheme
(page '(html (head (title "bjoweb"))
             (body (@ (class "card"))
                   (h1 "bjoweb")
                   (p "you asked for " (b ,what))
                   (hr)
                   (ul ,@rows))))
#+END_SRC

SXML, as a quoted literal. *No macro and no per-tag functions* — a quoted
literal with nesting in it stands for a union, and which case each piece becomes
is decided by its shape before anything is inferred: a symbol is a tag, a string
is text, a nested list is a child. See
~TestFiles/100_literal_elaboration.bjo~ in the compiler for the mechanism.

Which also means the tag vocabulary costs nothing and collides with nothing —
~a~, ~b~, ~p~, ~map~ and ~table~ are data here, not names.

- ~(@ (class "card") (id "main"))~ as the first child is the attribute list.
  A pair with no value is a boolean attribute: ~(@ (checked))~.
- ~,expr~ places one computed value, inside the *ordinary* quote — there is no
  backtick. It is chosen by its type: a ~string~ becomes text, a ~Raw~ is passed
  through unescaped.
- ~,@expr~ places the *elements* of a computed ~(List Node)~ where it stands,
  which is what a page driven by data needs. Anything written beside it is
  still elaborated the usual way, so ~'(ul (li "first") ,@rows)~ works. The
  spliced value is not elaborated — it is already a ~(List Node)~.
- A list whose head is not a symbol is a fragment, so ~'((li "a") (li "b"))~
  renders with no wrapper.
- Void elements — ~br~, ~img~, ~meta~, ~hr~ and the rest — get no closing tag.

*Text is escaped and attribute values doubly so*, which is the reason to have
this rather than string concatenation. ~,(raw "<em>x</em>")~ is the way past,
spelled as a call so that every place trust is claimed can be grepped for.

*** The output has newlines

Every node on its own line, two spaces a level, every line terminated. There is
no minified mode and no flag asking for one.

#+BEGIN_SRC html
<ul>
  <li>
    <a href="/page/banana">
      banana
    </a>
  </li>
</ul>
#+END_SRC

What that costs, because it is not free: a newline is whitespace, and HTML
collapses runs of whitespace to a single space in ordinary content. So
~'(p "a" (b "c") "d")~ is printed across four lines and a browser renders
~a c d~ rather than ~acd~. Indented markup and byte-exact inline text are not
both available, and this picks the first.

Where the text *is* the content — ~pre~ and ~textarea~ — nothing whatsoever is
added, child elements included, because indenting inside one of those does not
tidy it up, it edits it. Attribute values are never broken either: a newline in
one is not a nicety, it is a different value.

One sharp edge: an unquoted *number* is not chosen, because a numeric literal
stays polymorphic until it is defaulted — the error reads "'41' is a number, and
it is being used where a 'Node' is wanted". A number written literally in the
quote is fine; for a computed one write ~,(int->string n)~ or ~,(NInt n)~.

~render~ gives a string, ~document~ the same with a doctype, and ~page~ a whole
~Response~ with ~text/html; charset=utf-8~ on it.

** Routing

#+BEGIN_SRC scheme
(router
  (route-get    "/"                home)
  (route-get    "/users/:id"       show-user)
  (route-post   "/users"           create-user)
  (route-delete "/users/:id"       delete-user)
  (route-get    "/static/*path"    serve-file))
#+END_SRC

A pattern is split on ~/~. A piece beginning with ~:~ matches one segment and
binds it; a piece beginning with ~*~ matches everything left, slashes included,
and binds that; anything else is a literal. Empty pieces are dropped, so ~/a~
and ~/a/~ are one path.

First match wins, and *there is no specificity ranking*. Routes are evaluated in the order they are defined. Ensure more specific routes (like ~/users/new~) are listed before general ones (like ~/users/:id~).

Three things happen to a request:

- a route matches — its handler runs;
- the *path* matches but no route has that verb — 405, with the ~Allow~ header
  the RFC asks for and nobody sends;
- nothing matches — the fallback, which is a plain 404 until
  ~(with-fallback rt handler)~ says otherwise.

A ~HEAD~ with no ~HEAD~ route of its own is answered by the ~GET~ one.

~(route "OPTIONS" "/*path" preflight)~ is the general form, for verbs with no
helper.

** Running it

~serve~ is what a ~main~ wants: start, serve until Ctrl-C, stop.

#+BEGIN_SRC scheme
;; default values. Does not serve static files. 
(serve app #:port 8080 #:host "127.0.0.1" #:workers 16 #:queue 128 #:quiet #t #:static-files #f #:static-dir "wwwroot"
           #:trusted-proxies ["127.0.0.0/8" "::1"])
#+END_SRC

~start-server~ and ~stop-server!~ are the pair for a program that has something
else to do — a test, mostly:

#+BEGIN_SRC scheme
(with-scope
  (let ((server (start-server app #:port port)))
    (try
        (... use it ...)
      #:finally (stop-server! server))))
#+END_SRC

*Workers are spawned into the caller's scope.* Therefore, ~start-server~ must be used inside a ~with-scope~ that shouldn't end until ~stop-server!~ is called. Using ~serve~ handles this automatically.

~stop-server!~ stops Kestrel first and closes the inbox second. Kestrel's stop
waits for the requests already in the pipeline, and those are calls the workers
still have to answer — so the inbox has to be open while it runs. Closing it
afterwards is what tells the workers there will be no more.

*** The two numbers

~#:workers~ sets concurrency. ~#:queue~ sets how many requests can wait before the server returns a 503. The queue drops the *newest* requests to fail fast. 

A refused request returns ~503 Service Unavailable~ with ~Retry-After: 1~. This is handled gracefully without throwing exceptions in the middleware, avoiding unnecessary stack traces in Kestrel under load. ~(server-dropped-count server)~ returns the number of refused requests.

*** A client that goes away

The framework listens to Kestrel's ~RequestAborted~ token to detect disconnected clients:

- *Still queued:* The request is dropped and never reaches a worker.
- *Already processing:* The response is discarded and not written to the socket. The handler itself is *not* killed; it is allowed to finish to ensure side effects are safely completed.

*** Serving Static Files

You can opt into serving static files using Kestrel's highly optimized built-in static file server. Pass `#:static-files #t` to `serve` or `start-server`. By default, Kestrel will serve files out of a `wwwroot` directory in the current working directory, but you can override this by passing a different folder name to `#:static-dir`.

*** Behind a proxy

bjoweb speaks plain HTTP/1.1: no TLS, no HTTP/2. Facing the public, it belongs
behind a reverse proxy that does both. Caddy, for one, gets its certificates
itself and speaks HTTP/2 and HTTP/3 to the browser.

#+BEGIN_SRC
chat.example.com {
    reverse_proxy 127.0.0.1:8080
}
#+END_SRC

With the proxy on the same machine, keep the default ~#:host "127.0.0.1"~, so
that nothing reaches the server except through it.

The connection is then the proxy's, and what the client used arrives in
~X-Forwarded-For~, ~X-Forwarded-Proto~ and ~X-Forwarded-Host~ — which anybody
can send. So the server believes them only from a *trusted proxy*: loopback
unless told otherwise, which is right for a proxy on the same machine. A proxy
elsewhere has to be named:

#+BEGIN_SRC scheme
(serve app #:host "0.0.0.0" #:trusted-proxies ["10.0.0.0/8" "fd00::/8"])
#+END_SRC

Each is an address or a network with a prefix length; a host name, or anything
else that is neither, stops ~serve~ or ~start-server~ with an
~ArgumentException~. ~[]~ trusts nobody.

- ~(request-client req)~ :: ~X-Forwarded-For~, read from the right. Every proxy
  on the way appends the address it was reached from, so the first address
  from the right that is not a trusted proxy is the client, and whatever is
  left of it the client may have written itself.
- ~(request-scheme req)~ and ~(request-host req)~ :: ~X-Forwarded-Proto~ and
  ~X-Forwarded-Host~, or the connection and the ~Host~ header when the proxy
  sends none.

From anywhere else, the three headers are ignored, and the three functions say
what the connection says. ~request-header~ shows the headers as they came
either way, so the client is ~request-client~'s answer, not the header's. The
~Forwarded~ header of RFC 7239 is not read.

Trusting a proxy means trusting it to set all three, rather than pass on what
the client sent. Caddy does. nginx sets only the ones its configuration tells
it to, and passes the others on as they came.

The host is the client's to choose, behind a proxy or not, as the ~Host~
header always was. A link that goes out by email is better built from a name
the program knows.

Through Caddy, a streamed body goes out as it is written, because Caddy flushes
a response of unknown length at once. A websocket is proxied too, and closed
when Caddy reloads its configuration, so a page that keeps one open should
reconnect.

** What this is not

No dependency injection, no configuration system, no authentication, no content
negotiation, no TLS, no HTTP/2, no streamed request bodies. Kestrel can do all
of those and none of them is here; a reverse proxy in front does TLS and HTTP/2
(see Behind a proxy). Websockets are here, without the compression extension,
and so are streamed response bodies and server-sent events.

~(bjoweb server)~ exports ~Ctx~ — the ~HttpContext~ type itself — so a program
that needs one of them can reach for it, and so that reaching for it is visible.

** Installing it

It is an ordinary ~bjo~ package. From a project of your own:

#+BEGIN_SRC scheme
(depends
  (package (name (bjoweb))
           (version (version-at-least "0.1.1"))
           (source (git (url "https://github.com/bjoli/bjoweb")))))
#+END_SRC

~(net websocket)~, from [[https://github.com/bjoli/websocket]], comes along with
it. bjoweb needs a Bjolang whose ~(std net)~ has ~stream->ports~, and from
0.1.1 on one where closing a byte output port writes only what is pending. From
0.2.0 on it also needs one where ~utf8~ writes no byte order mark and a call
handed to a waiting receiver is taken. See Bjolang's changelog for all three.

Note that *the ASP.NET runtime has to be installed wherever the program runs*.
Not just where it is built: a framework-dependent program asks the host for
~Microsoft.AspNetCore.App~ at startup. The Docker image ~dotnet/runtime~ does
not have it; ~dotnet/aspnet~ does.

** Running the tests

#+BEGIN_SRC sh
bjo run tests/html.bjo    ;; 33 checks, no server anywhere
bjo run tests/demo.bjo    ;; 71 checks, a real socket
#+END_SRC

~tests/html.bjo~ is the renderer on its own: shapes and indentation, attributes,
boolean attributes, void elements, ~pre~ and ~textarea~ left byte for byte,
escaping in text and in attribute values, that an attribute value never gains a
newline, computed content through ~,~, ~raw~, fragments, and the document and
response wrappers.

Seventy-one checks: the routing table on its own, then a real Kestrel on a port
the test picks, fetched over a socket with ~(std http)~ — percent-encoded paths,
query strings, request headers, a POST body, a suspending handler, a handler
that raises, the 404 and the 405, a redirect, and twelve requests at once
through four workers, each getting the answer to its own question. Then a second
server with one worker and one queue slot, to see that six at once come back
~200x2 503+retry-after=1x4~ and that it still serves afterwards.

Bodies are checked byte for byte over a plain TCP socket, because ~(std http)~
drops a byte order mark while it decodes: text goes out as UTF-8 with none,
bytes go out as they are, and a 204 sends nothing whatever its handler gave it.
And ~Content-Length~: in bytes rather than characters, 0 for an empty body, the
~GET~'s for a ~HEAD~, and the body's even when the handler put another one in
the headers.

Streamed bodies are read over a plain socket too, to see what arrives when and
how the body ends: a streamed body and streamed text, with no ~Content-Length~;
the first part arriving while the writer is still waiting to write the second;
a writer that raises, whose response is cut off rather than ended; a client
that hangs up, which stops the writer; and a ~HEAD~, which never calls it.
Then a server with one worker, which still serves a plain request while a
stream is open, and which is stopped with the stream open: the stop does not
wait for it, the stream is cut off rather than ended, and its writer stops.

Server-sent events: the exact text of a stream — the opening comment, the
retry, an event with a name and an id, data with a line break in it — and its
headers; a keep-alive on a quiet stream; a line break in an event name
refused, with nothing of it sent and the stream cut off; and a sink kept past
its stream, which answers ~#f~ rather than waiting.

It also checks the thing this framework is for: a parameter installed around
~start-server~ is readable inside a handler. Kestrel's thread never had it.

The test's client is on loopback, so to the first server it is a trusted proxy:
its ~X-Forwarded-*~ are believed, but not an address written left of the one
it added, and a trusted proxy further out is looked past. A server told to
trust only other networks ignores the same headers, and one told to trust a
host name does not start.

Then websockets, with ~websocket-connect~ as the client: an echo of text and
binary, a session that returns and one that raises, a subprotocol, a middleware
refusing before the upgrade and letting the right request through, ~426~ for a
plain GET, six sockets held open through four workers while a plain request is
still served — and a third server stopped with a socket open, which has to close
it with 1001 rather than wait for it.
